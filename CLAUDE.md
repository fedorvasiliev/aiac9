# aiac9 — заметки для AI-ассистента

Проект — Go-приложение (CLI с возможностью поднять HTTP-сервер),
изначально сгенерированный как отправная точка для разработки с помощью AI.
Назначение конкретного продукта - работа с LLM моделями через API. 
В качестве основого способа взаимодействия с оператором (пользователь, человек) используется командная строка.

## Основная функциональность

- Запуск без аргументов (`aiac9`) включает интерактивный консольный режим
  вопрос/ответ: см. `internal/interactive`. 
- Подкоманды (`serve`, `version`, `help`) — см. `internal/cli`.

Программа должа уметь отправлять запросы в LLM по API - для этого нужно воспользоваться примерами из папки ./api-examples

Например, для всех моделей kimi необходимо использовать контракт описанный в kimi-completions.txt

Значения переменных объявленные через $ (например $MOONSHOT_API_KEY) - должны браться из переменных окружения. 
Все значения которые беруться из перемнных откружения при логировании в файлы и отображении на экране - должны маскироваться звездочками (***).

Для моделей deepseek необходимо брать контракт из официальной документации https://api.deepseek.com/chat/completions
Запросы (если явно не сказано иное) отправляются на endpoint /chat/completions

Каждая пара запроса и ответа логируется в папку ./logs
Паттерн имен файлов логов: <day of month>-<month name>-<24 format hour>-<minutes>-<seconds>-<model name>.log
Запрос логируется прямо перед отправкой.

### Логика интерактивного режима
Состоит из последовательных шагов взаимодействия оператора и программы.
Результаты каждого шага сохраняются (накапливаются) внутри программы для дальнейшей отправки в LLM через API.
Типы интерфейсных элементов:
- строка ввода текста (или input). enter приводит к завершению текущего шага.
- интерактивный список выбора (или select или список выбора). стрелки вверх/вниз/пробел - прокручивают список покругу. слово default - означает что элемент выбран по умолчанию. enter приводит к завершению текущего шага.

Все интерактивные элементы имеют заголовок (или label) - текст приглашающий к вводу или выбору. Текст Label должен быть желтого цвета.

В лог пишем общее время исполнения запроса.

### Вывод в консоль диалога пользователя с моделью
Полученный от Модели ответ выводится в терминал текстом зеленого цвета.
После каждого взаимодействия с моделью выводим в терминал:
```
\n
prompt_tokens: <count>, completion_tokens: <count>\n
dialog prompt_tokens: <count>, dialog completion_tokens: <count>\n
общее время исполнения запроса (с точностью до сотых долей секунды)
```

#### "Шаг D"
Шаг выбора диалога.
Список диалогов берется из таблицы dialog.
По умолчанию выбран пункт - "/new" (default).
Если пользователь выбрал пункт /new - необходимо начать новый диалог.
Если выбран один из существующих диалогов - необходимо взять историю этого диалога из таблицы dialog - обоготить ей system prompt и отправить его при следующем запросе в LLM.
Если для диалога существует summary (таблица dialog_summary) - его так же необходимо добавить к system prompt.
В консоли необходимо вывести последние 2 вопроса и ответа из истории диалога (выводим в стандартном виде).
Если диалог продолжается в интерактивном режиме каждый новый запрос-ответ диалога должен быть записан в историю диалога (таблица dialog) и должен обогощать текущий system prompt.

Тип: select

Заголовок: Dialog

#### "Шаг A"
Шаг выбора предзаполненного prompt. Список для отображения необходимо брать из папки ./prompts во время исполнения программы (не во время компилации).
Если при запуске программы ей был передан cli-флаг -f со значением отличным от пустой строки (например: -f w1d4) - необходимо в списке выбора отображать только 
те промпты в имени которых содержится это значение (например: any-w1d4.prompt.md).
Подробнее о логике работы этого модуля - смотри раздел "Парсинг заготовленных промптов"

Тип: select

Заголовок: Use prompt

Первый элемент списка выбранный по умолчанию - "Пользовательский промпт" (default)

#### "Шаг T"
Терминальный шаг. Всегда идет последним. Приводит к сборке и отправке запроса в модель по API (учитываются все предыдыщие шаги).
Допускается введение пустого значения.
Если введено непустое значение - необоходимо дополнить им все user prompt и отправить запрос.

Пока модель обрабатывает результат в консоле должен выводиться анимированный Loader/Spinner.

Тип: input

Label: Дополнитить user prompt и отправить

### Парсинг заготовленных промптов
Когда пользователь выбрал один из промптов на шаге "Шаг A" - необходимо в реальном времени распарсить соотвествующий файл
и обоготить формируемый для отправки запрос следующий образом:
- Заголовок Model - предписывает взять версию моделе из этого абзаца 
- Заголовок "System prompt" говорит о том что внутри этого абзаца будет системный промпт - его необходимо будет передать 
модели в отдельном message c ролью messages.role=system
- Заголовок "User prompt" говорит о том что внутри этого абзаца будет user prompt - его необходимо будет передать
  модели в отдельном message c ролью messages.role=user 
Таких заголовков может быть несколько - в этом случае каждый передается в отдельном message 
- Заголовок "Response format" говорит о том что внутри этого абзаца будет формат ответа - это значение необходимо передать
  модели в поле response_format.type
- Заголовок "Words limit" говорит о том что внутри этого абзаца указано число - его необходимо добавить в текст
"Максимальное количество слов в ответе должно быть <это число>." - и всю получившуюся фразу добавить ко всем user prompt 
  модели в поле response_format.type
- Заголовок "Stop" - говорит о том что внутри этого абзаца будет stop_sequence которая приводит к оставке генерации ответа моделью.
stop_sequence необходимо передать в поле stop
- Заголовок "Temperature" - из этого абзаца берем значение для поля temperature

После парсинга всего файла необходимо вывести в терминал все что получилось, в формате таблицы.

| Параметр      | Значение                   |
|---------------|----------------------------|
| Model         | <Значение для Model>       |
| ...           | ...                        |
| <Заголовок N> | <значение для Заголовок N> |

Текст в первой колонке - желтый.
Если значение пустое - соотвествующую ему строку - не печатаем.

Если длина значения любого из полей больше 80 символов - необходимо выводить не в табличной форме - а в следующем формате:
```
<Заголовок 1>:
<значение для Заголовок 1>

<Заголовок N>:
<значение для Заголовок N>
```
Текст заголовка - желтый.

## Техническая конфигурация

Таймауты ожидания соединения - 30 секунд.
Таймаут ожидания ответа - 180 секунд.

Если при запуске программы ей был передан cli-флаг -timeout со значением отличным от пустой строки (например -timeout 300)
необходимо переопределить Таймаут ожидания ответа - взяв переданное значение (будет указан в секундах)

## Диалоги
Добавляем понятие диалога между моделью LLM и оператором.
Новый Диалог инициируется консольной командой /clear или /new
Каждый диалог должен обрабатываться в отдельной goroutine - в будущем будет необходима возможность запуска десятков и сотен паралельных взаимодействий (диалогов) с сервером LLM.

### Работа с историей диалогов
История диалогов хранится в таблице dialog в SQLite.
Контекст диалога необходимо брать из запроса ("role":"user" и "role"":"system") и ответа модели ("role":"assistant") - в обоих случаях используем поле message.content
Сохраняем в таблицу dialog "prompt_tokens" - в строчку с запросом и "completion_tokens" в строчку с ответом.

Для каждого диалога храним последние HISTORY_MSG_COUNT (берется из файла ./aiac9.config) запросов и столько же соответствующих ответов.
Суммаризация диалога хранится в таблице dialog_summary.
Если конфигурационная переменная HISTORY_SUMMARIZATION - включена - то старые сообщения (старше HISTORY_MSG_COUNT) - необходимо отправить в LLM для сжатия (method /chat/completions последней использованной модели) - пример промпта:
```
Обоготи текущее summary диалога: <подставить текущее summary из таблицы dialog_summary>

Следующими сообщениями: 
user message - <запрос юзера> 
assistant message - <ответ LLM> 

Результирущее summary - должно быть коротким и лаконичным

```
Получившееся summary необходимо сохранить в таблицу dialog_summary обновив соответствующую диалогу строчку.
После этого старые сообщения необходимо удалить из таблицы dialog.

### Context Strategy
Конфигурируется переменной CONTEXT_STRATEGY - варианты значения и логика работы:

- Sliding_Window - все сообщения кроме последних HISTORY_MSG_COUNT - удаляются из dialog.
- STICKY_FACTS - для каждого диалога необходимо сохранять факты (ключ-значение) в таблицу facts, для этого к каждому запросу в LLM необходимо добавить промпт: вычлени из user prompt факты (ключ-значение) и добавь их к твоему ответу в отдельной секции фактов. Секцию фактов из ответа необходимо сохранить в таблицу facts. Все сообщения кроме последних HISTORY_MSG_COUNT - удаляются из dialog. При этом все сохраненные для данного диалога факты добавляются в system prompt и отправляются с очередным запросом.

## Конвенции

- Только стандартная библиотека, без внешних зависимостей, пока в этом нет
  явной необходимости — при добавлении зависимости объясняйте, зачем.
- Весь код приложения — в `internal/`, `cmd/aiac9/main.go` остаётся тонким.
- Конфигурация (`internal/config`) — через переменные окружения и конфигурационный файл ./aiac9.config, переменные окружения - перезаписывают значения из файла
- В конфигурации значения переменных: on, 1, yes - трактуем как "включено"; off, 0, no - как "выключено". 
- Версия/коммит/дата сборки подставляются через `-ldflags` (см. `Makefile`),
  не хардкодить.
- локальный SQLite последней версии для хранения истории диалогов
